# 类别六：核心AI特性与集成



## 1. 场景：当AI模型返回一个FunctionCall（例如{"name": "get_weather", "arguments": {"city": "Beijing"}}）时，请设计后端的工作流程：如何安全地解析、路由到对应的工具实现、执行（可能调用外部API）、并将结果格式化后返回给AI模型？

**核心思路**：

1. **解析与验证**：首先，安全地解析AI模型返回的JSON，提取函数名和参数。验证函数名是否在允许的工具列表中，参数是否符合预定义的JSON Schema（可使用JSON Schema校验库）。此步骤可防止执行未授权或参数不合法的函数。
2. **路由与执行**：维护一个工具注册表，将函数名映射到具体的工具执行器。每个工具执行器是一个独立的类，负责调用对应的外部API或内部服务。根据函数名从注册表中获取执行器，注入参数，执行工具。执行过程应设置超时和重试机制。
3. **结果格式化**：工具执行成功后，将结果格式化为AI模型期望的结构（例如，包含`tool_call_id`和`content`字段）。如果执行失败，返回错误信息，AI模型可根据错误决定下一步操作。
4. **安全性考虑**：工具执行可能涉及敏感操作，应基于当前用户上下文进行权限检查。工具调用应记录审计日志，便于追踪。
5. **返回AI模型**：将格式化后的工具调用结果作为新的消息附加到对话上下文中，再次调用AI模型，让AI模型基于工具执行结果继续生成回复。



## 2. 场景：在RAG系统中，用户提问“公司最新的年假政策是什么？”。请描述后端完整的处理链条：从接收问题，到将其向量化，在向量数据库中检索相关片段，再到组装包含上下文的Prompt发送给AI，最后返回答案。

**核心思路**：

1. **问题向量化**：使用与知识库文档相同的嵌入模型（embedding model）将用户问题转换为向量表示。
2. **向量检索**：在向量数据库（如Milvus、Pinecone）中执行相似性搜索，检索与问题向量最相关的K个文本片段。通常还会使用元数据过滤（例如，只检索“年假政策”相关的文档）。
3. **重排序（可选）**：使用更精细的交叉编码器（cross-encoder）对检索结果进行重排序，提高相关性。
4. **上下文组装**：将检索到的相关文本片段与用户问题组合成Prompt。常见的模板是：”基于以下上下文回答问题：{context} 问题：{question}“。确保总Token数不超过模型的上下文限制。
5. **调用AI模型**：将组装好的Prompt发送给AI模型（如GPT-4），获取生成的答案。
6. **返回答案**：将AI生成的答案返回给用户，并可选择附带引用来源（即检索到的片段），增加可信度。
7. **缓存**：对常见问题可缓存检索结果和生成的答案，以降低延迟和成本。



## 3. 场景：请用代码草图展示，如何利用Spring的@EventListener或消息队列，实现一个简单的工作流：用户提问->触发意图识别AI->根据意图（如“翻译”或“总结”）路由到不同处理AI->聚合结果。

**核心思路**：

1. **事件驱动设计**：定义领域事件，如`UserQuestionReceivedEvent`（包含问题内容、用户ID等）。
2. **意图识别**：使用`@EventListener`监听`UserQuestionReceivedEvent`，调用意图识别AI服务（可封装为Spring Bean），确定意图（如翻译、总结）。然后发布新的意图特定事件，如`TranslationRequestEvent`或`SummaryRequestEvent`。
3. **路由处理**：为每种意图定义对应的事件监听器。例如，`TranslationRequestEvent`由翻译服务监听，调用翻译AI；`SummaryRequestEvent`由总结服务监听，调用总结AI。
4. **聚合结果**：每个处理服务处理完后，发布结果事件（如`TranslationCompletedEvent`），由聚合服务监听并聚合结果。聚合服务可维护一个状态机，等待所有子任务完成，然后返回最终结果给用户。
5. **消息队列替代**：如果服务是分布式的，可使用消息队列（如RabbitMQ、Kafka）替代Spring事件。将事件发布到消息队列，不同服务订阅对应Topic，实现解耦和异步处理。
6. **错误处理与补偿**：某个步骤失败时，发布失败事件，触发补偿操作（如重试或通知用户）。



## 4. 场景：你需要设计一个“模型路由”服务。根据请求的属性（如语言是中文还是英文、需求是创意写作还是逻辑推理、预算高低），动态选择最合适的AI模型（如GPT-4，Claude-3，国产大模型）进行调用。请设计路由规则的数据结构和匹配逻辑。

**核心思路**：

1. **路由规则定义**：每条规则包含条件（condition）和目标模型（model）。条件可基于请求属性：语言（枚举）、任务类型（枚举）、预算（数值范围）、内容长度等。规则可配置，支持优先级。

2. **数据结构**：可使用List存储规则，按优先级排序。每个规则是一个对象，包含条件表达式和目标模型。条件表达式可以使用DSL（领域特定语言）或简单的POJO表示，例如：

   ```
   class RoutingRule {
   		Condition condition;
   		String model;
   		int priority;
   }
   class Condition {
   		String language; // 可选值：中文、英文等 
   		String taskType; // 创意写作、逻辑推理等
   		Range budget;    // 预算范围
   }
   ```

3. **匹配逻辑**：收到请求后，按优先级遍历规则列表，评估条件是否满足。第一个满足的条件对应的模型即为目标模型。如果没有匹配，使用默认模型。

4. **评估引擎**：条件评估可以基于简单的if-else，也可以使用规则引擎（如Drools）实现复杂逻辑。

5. **动态更新**：路由规则可存储在配置中心或数据库，支持热更新。服务监听配置变更，重新加载规则。

6. **上下文传递**：路由服务可以附加到AI调用客户端，在调用前根据请求属性选择模型。也可以作为独立的网关服务。

（模型路由本身是一个基础设施决策，最好不要完全交给另一个 LLM。所以可以模型+规则，预先小模型做各字段分类，再规则系统路由判断）



## 5. 场景：在“AI辅助编程”场景，用户选择一段代码并请求“解释”。后端需要将代码和指令发送给AI。请设计一个Prompt模板系统，允许管理员根据不同编程语言（Java, Python, JavaScript）动态配置和优化对应的解释性Prompt。

**核心思路**：

1. **模板存储**：将Prompt模板存储在数据库或配置中心。每个模板关联编程语言、用途（如解释、重构、调试等）。模板内容可包含变量占位符，如`{code}`、`{language}`。
2. **模板设计**：针对不同语言设计不同的解释模板。例如，Java的模板可能强调面向对象概念，Python的模板可能强调简洁性。模板可由管理员通过管理界面编辑。
3. **变量替换**：在运行时，根据用户选择的语言和代码，从数据库加载对应模板，将变量替换为实际值，生成最终Prompt。
4. **模板版本管理**：支持模板的版本控制，便于回滚和A/B测试。
5. **默认回退**：如果某种语言没有特定模板，使用通用模板。
6. **集成**：在代码解释服务中，调用模板渲染器生成Prompt，然后调用AI模型。
7. **扩展性**：模板系统可设计为支持多种任务，不限于解释，还可用于代码生成、注释生成等。



## 6. 场景：如何实现一个简单的“模型熔断与降级”策略？当首选模型（如GPT-4）连续失败或超时时，自动将流量切换到备选模型（如GPT-3.5），并在首选模型恢复后逐步切回。

**核心思路**：

1. **熔断器模式**：为每个模型客户端配置熔断器（如使用Resilience4j）。监控调用失败和超时，当失败率超过阈值，熔断器打开，后续请求快速失败，不调用实际服务。
2. **降级策略**：在熔断器打开时，执行降级逻辑，即切换调用备选模型。可以在代码中通过try-catch捕获熔断异常，然后调用备选模型。
3. **恢复探测**：熔断器进入半开状态时，允许部分请求通过，如果成功则关闭熔断器，恢复使用首选模型。
4. **配置化**：熔断器的参数（失败阈值、等待时间等）和降级模型列表可配置，便于调整。
5. **平滑切回**：恢复初期，可以仅将少量流量切回首选模型，逐步增加比例，避免再次压垮。
6. **状态管理**：熔断器状态可存储在内存中，对于分布式服务，需考虑状态共享（如使用Redis），确保集群内行为一致。



## 7. 场景：对于“生成周报”这种长文本任务，AI的上下文窗口可能不够。请设计一个“分而治之”的算法：将任务拆分成多个子问题（如按项目拆分），分别调用AI，最后将结果合并。需要注意哪些问题（如子任务间的连贯性）？

**核心思路**：

1. **任务分解**：根据周报的结构（如按项目、按日期）将长文本拆分成多个独立的子任务。每个子任务包含具体的要点和上下文。
2. **并行处理**：将子任务并行提交给AI模型（注意API的速率限制），收集所有结果。
3. **结果合并**：设计一个合并策略，将子结果拼接成完整的周报。可能需要额外的AI调用对合并后的文本进行润色，确保连贯性。
4. **连贯性保证**：在拆分时，可以为每个子任务提供全局上下文摘要，确保每个部分与整体一致。合并后，可调用AI进行整体润色，消除重复和矛盾。
5. **错误处理**：某个子任务失败时，可选择重试、跳过或使用默认内容。
6. **进度反馈**：对于长任务，可实时返回处理进度，提升用户体验。
7. **成本与延迟权衡**：并行可降低延迟，但可能增加Token消耗（因为每个子任务都需要上下文）。需根据实际情况调整拆分粒度。



## 8. 场景：在多轮对话中，如何管理不断增长的上下文？请实现一个“智能摘要”策略：当对话轮数或Token数超过阈值时， 自动调用AI对早期对话进行摘要，并用摘要替换掉原始冗长的历史，以节省Token并保持核心信息。

**核心思路**：

1. **上下文窗口监控**：维护当前对话的Token总数，当接近模型上下文限制时触发摘要。
2. **摘要生成**：选择早期的一部分对话（如最旧的N轮），调用AI生成摘要。Prompt可设计为：“请将以下对话摘要为一段简洁的文字，保留关键信息和决定：{早期对话}“。
3. **上下文替换**：用生成的摘要替换原始的早期对话，并将摘要作为一条系统或用户消息插入到上下文头部。同时，更新Token计数。
4. **摘要策略**：可配置摘要的触发条件（Token数或轮数）和摘要范围。也可定期摘要，而不是仅在接近限制时。
5. **保持连贯性**：摘要应保留对后续对话必要的关键信息，如用户偏好、已做出的决定等。
6. **迭代摘要**：如果对话非常长，可能需要进行多次摘要，形成摘要的摘要。注意避免信息损失过多。
7. **实现**：在对话管理服务中封装此逻辑，在每次添加新消息前检查Token数，必要时触发异步摘要。



## 9. 场景：请设计一个“多模型投票”机制。将同一个问题发送给三个不同的AI模型，收集它们的回答，然后通过一个“裁判”模型或基于规则的方法（如选择最简、最符合格式要求的）选出最终答案。如何实现并行调用和结果聚合？

**核心思路**：

1. **并行调用**：使用`CompletableFuture`或反应式编程并行调用三个AI模型。为每个调用设置超时，避免某个模型响应过慢拖慢整体。
2. **结果收集**：等待所有调用完成（或超时），收集成功返回的结果。
3. **投票策略**：
   - **裁判模型**：将问题和所有答案发送给一个裁判模型（如GPT-4），让其选择最佳答案或生成综合答案。
   - **规则投票**：基于规则选择，例如：选择最简洁的答案（字符数最少）、最符合格式的答案（如包含特定关键词）、或使用一致性投票（多数胜出）。
4. **聚合**：如果使用裁判模型，则其输出为最终答案。如果使用规则，则应用规则选择答案。
5. **错误处理**：如果某个模型失败，可忽略其答案。基于剩余答案投票。如果所有模型失败，返回错误。
6. **成本考虑**：多模型投票成本较高，适用于关键任务。可对高价值问题启用。
7. **监控**：记录每个模型的回答和投票结果，用于后续分析和模型评估。



## 10. 场景：你需要集成一个本地的开源大模型（如通过Ollama部署的Llama 3）。请描述Java后端如何通过HTTP或gRPC与这个本地模型服务交互，并处理与商用API在响应格式上的差异。

**核心思路**：

1. **客户端选择**：如果本地模型服务提供HTTP API（如Ollama），可使用Spring的`WebClient`或`RestTemplate`进行调用。如果提供gRPC接口，可使用gRPC Java客户端。
2. **统一接口**：定义统一的AI客户端接口，针对不同模型实现适配器。这样业务代码不依赖具体模型。
3. **请求适配**：将内部统一的请求格式转换为本地模型所需的格式。例如，Ollama的API格式与OpenAI不同，需要映射字段。
4. **响应适配**：将本地模型的响应转换为内部统一格式，确保后续处理一致。注意处理可能的结构差异，如字段名不同、嵌套层次不同。
5. **错误处理**：本地模型可能返回不同错误码和消息，需要转换为内部错误类型。
6. **性能考虑**：本地模型通常部署在内网，延迟较低，但也要设置合理的超时。gRPC通常性能优于HTTP。
7. **配置管理**：本地模型的端点、端口等配置化，便于不同环境部署。
8. **健康检查**：定期检查本地模型服务是否健康，不可用时触发熔断或警告。



## 11. 场景：在AI绘画中，用户可能会多次调整参数（如“更明亮一些”、“增加一个小孩”）进行迭代。请设计一个会话机制，能够基于上一张图片的生成参数和种子（seed）进行微调，而不是完全重新生成。

**核心思路**：

1. **会话管理**：为每个用户绘画会话创建唯一ID，存储该会话的历史生成记录，包括每次生成的参数、种子、生成的图片URL。
2. **参数继承**：当用户请求调整时，从会话中获取上一次生成的参数和种子，作为基础。将用户的调整描述（如“更明亮一些”）转换为具体的参数调整（如增加亮度值）。种子可以保持不变或微调，以保证输出的一致性。
3. **提示词演化**：如果用户调整涉及提示词，可将新指令附加到原提示词后，或使用AI理解用户意图生成新提示词。
4. **生成与存储**：调用会话AI（如Stable Diffusion）时，使用调整后的参数和种子，生成新图片。存储新纪录到会话历史。
5. **版本树**：会话历史可形成版本树，支持回到任意历史版本继续调整。
6. **性能优化**：如果调整较小，可以使用img2img功能，基于上一张图片生成，而不是完全从头生成。
7. **用户界面**：前端可展示调整历史，允许用户选择任一历史版本继续编辑。



## 12. 场景：如何实现一个“函数注册表”，允许系统在运行时动态注册新的工具函数（如search_web, query_database）及其JSON Schema，供AI模型在Function Calling时使用？

**核心思路**：

1. **注册表设计**：使用内存中的Map存储函数名到工具描述的映射。工具描述包括函数名称、描述、参数JSON Schema、以及执行该函数的Bean或方法。
2. **动态注册**：暴露管理端点，允许管理员通过HTTP注册新工具。注册时，提供函数名、描述、参数Schema和执行器类名。系统根据类名通过Spring上下文获取Bean，或使用反射创建实例。
3. **模式校验**：使用JSON Schema校验库（如`everit-org/json-schema`）校验AI模型传入的参数是否符合注册的Schema。
4. **执行路由**：当AI模型返回函数调用时，根据函数名从注册表中获取执行器，校验参数后执行。
5. **热更新**：注册表支持添加、删除、更新工具，无需重启服务。注意线程安全。
6. **持久化**：可将注册的工具信息持久化到数据库，服务启动时加载，避免重启丢失。
7. **权限控制**：工具注册和调用应有权限控制，防止恶意注册或调用。
8. **示例**：Spring Boot中，可使用`ApplicationContextAware`获取Spring容器，动态注册Bean。但注意，工具执行器通常应为无状态单例。



## 13. 场景：设计一个”思维链（Chain-of-Thought）”的调用模式。首先让AI输出其推理过程，然后根据内部规则对推理过程进行校验或提取关键步骤，最后再输出最终答案。如何在服务端协调这个多步过程？

**核心思路**：

1. **两步Prompt**：设计两个Prompt。第一个Prompt要求AI逐步推理，并输出推理过程。第二个Prompt要求AI基于推理过程给出最终答案，并可选择性地要求其以特定格式输出。
2. **协调流程**：
   - 调用AI模型，使用第一个Prompt，获取包含推理过程的响应。
   - 服务端解析响应，提取推理过程文本。
   - 可选：对推理过程进行校验，如使用规则检查是否包含关键步骤，或调用另一个校验模型。
   - 将推理过程作为上下文，调用AI模型（可以是同一模型）使用第二个Prompt，获取最终答案。
3. **单次调用实现**：也可以设计一个Prompt，要求AI在单个响应中先输出推理过程，然后输出最终答案，并用特定分隔符隔开。服务端解析响应，拆分两部分。
4. **错误处理**：如果推理过程不符合要求（如缺失步骤），可重试或直接返回错误。
5. **缓存**：对相同问题，可缓存推理过程，加速后继续相同问题的处理。
6. **可观测性**：记录推理过程和最终答案，用于分析和改进。



## 14. 场景：在知识库问答中，如何实现”引用溯源“？即，在返回答案的同时，高亮显示答案来源于知识库中的哪几个原文片段。请设计返回的数据结构以及前端交互所需的标注信息。

**核心思路**：

1. **数据结构**：返回的答案应包含答案文本和引用列表。每个引用指向一个原文片段，包含片段ID、原文文本、在原文中的起止位置、来源文档、置信度等。

2. **答案生成**：在RAG的Prompt中，要求AI模型在生成答案时引用相关片段，例如使用特殊标记如`[1]`。或者，在检索到相关片段后，将每个片段编号，并在Prompt中要求AI使用编号引用。

3. **后端处理**：解析AI返回的答案，提取引用标记，与检索片段关联。如果没有显式引用，可以使用相似度计算将答案句子与片段关联。

   ```

   			"id": 1,
   			"text": "原文片段内容...",
   			"document": "员工手册.pdf",
   			"page": 5,
   			"start": 10,
   			"end": 50
   		}
   	]
   }
   ```

5. **前端交互**：前端收到响应后，将答案中的引用标记渲染为可点击的链接或悬停提示。点击引用可以跳转到原文片段，或在侧边栏显示原文。
6. **高亮显示**：前端可根据引用中的起止位置，在原文中高亮显示对应文本。
7. **扩展**：支持多个引用，以及引用在答案中的多个位置。



## 15. 场景：用户要求“用莎士比亚的风格写一首关于春天的诗”。请设计一个两阶段Prompt：第一阶段让AI分析“莎士比亚风格”的特点；第二阶段基于分析结果进行创作。如何在服务端串联这两个AI调用？

**核心思路**：

1. **第一阶段Prompt**：设计Prompt让AI分析莎士比亚风格的特点，例如：“请总结莎士比亚写作风格的主要特点，包括语言风格、常用主题、修辞手法等。”保存分析结果。
2. **第二阶段Prompt**：将第一阶段的分析结果作为上下文，设计创作Prompt：“基于以下对莎士比亚风格的分析：{分析结果}，创作一首关于春天的诗，要求符合莎士比亚风格。“
3. **串联调用**：服务端先调用AI模型（可以是同一个模型）完成第一阶段，得到分析结果。然后，将分析结果嵌入第二阶段的Prompt，再次调用AI模型得到最终的诗。

5. **错误处理**：如果第一阶段失败，可重试或使用预定义的分析结果。
6. **可扩展性**：此模式可推广到任何需要先分析再创作的任务，例如模仿其他作家风格、遵循特定指南等。



## 16. 场景：当AI在处理用户请求时，可能需要询问用户以澄清模糊意图（如“您指的是北京还是南京？”）。请设计一个中断-恢复机制：暂停当前AI处理流程，将问题返回给用户，并在收到用户回复后，从暂停点继续执行。

**核心思路**：

1. **状态管理**：为每个用户会话维护一个状态机，状态包括：处理中、等待用户澄清、已完成等。当AI需要澄清时，状态转为等待用户澄清。
2. **上下文保存**：在中断时，保存当前的对话上下文、AI已生成的中间结果、以及需要澄清的点。这些信息可存储到数据库或缓存，键为会话ID。
3. **返回用户**：将AI的澄清问题返回给用户，并提示用户回复。
4. **恢复**：当收到用户的回复后，根据会话ID加载保存的上下文，将用户回复作为新消息附加到上下文中。然后，继续AI处理流程，从上次中断点继续（例如，重新调用AI模型，或继续执行后续步骤）。
5. **超时处理**：设置等待澄清的超时时间，超时后取消任务或执行默认选择。
6. **实现**：可以在AI工具调用中实现，当工具需要更多参数时，抛出特定异常，由上层捕获并触发澄清流程。或者，在AI生成的内容中检测到澄清需求，通过解析AI响应触发。
7. **用户体验**：前端需支持显示澄清问题，并允许用户回复，保持会话连续性。



## 17. 场景：如何对AI生成的代码进行“后处理”？例如，自动调用代码格式化工具（如Prettier）、进行基础的静态检查、或者插入相关的import语句。请设计一个可插拔的后处理器管道。

**核心思路**：

1. **管道模式**：设计一个处理器管道，每个处理器负责一个后处理步骤，如格式化、静态检查、导入优化等。处理器按顺序执行，上一个处理器的输出作为下一个的输入。

2. **处理器接口**：定义统一接口，例如：

   ```
   interface CodePostProcessor {
   		String process(String code, String language);
   }
   ```

3. **可插拔**：通过Spring的依赖注入，将所有实现`CodePostProcessor`的Bean收集到一个List中，按顺序执行。新增处理器只需实现接口并注册为Spring Bean。
4. **配置化**：每个处理器可配置启用/禁用，以及参数（如格式化风格）。
5. **错误处理**：某个处理器失败时，可记录错误并跳过，继续执行下一个，保证管道不中断。
6. **语言特定**：处理器可根据代码语言选择不同的处理逻辑，如Java使用Google Java Format，Python使用black。
7. **外部工具调用**：有些处理器可能需要调用外部命令行工具（如Prettier），需确保环境已安装相应工具，并处理调用异常。
8. **缓存**：对于相同代码，可缓存后处理结果，提高性能。



## 18. 场景：在“AI法律顾问”场景，生成的法律文本需要插入准确的条款引用（如“根据《XX法》第N条...“）。请设计一个RAG流程，从法律条文数据库中检索相关条款，并将其作为上下文提供给AI模型。

**核心思路**：

1. **法律条文向量化**：将法律条文数据库（每条包含法律名称、条款号、条款内容）切片并向量化，存入向量数据库。
2. **用户问题分析**：当用户提出法律问题时，将问题向量化，在向量数据库中检索最相关的K个法律条款。
3. **Prompt组装**：将检索到的条款作为上下文，与用户问题一起组装成Prompt。Prompt可设计为：”请基于以下法律条款回答问题：{条款1} {条款2} ... 问题：{用户问题} 请引用相关条款号。“
4. **AI生成**：调用AI模型生成答案，要求模型在答案中引用具体条款。（可使用Few-shot prompting）
5. **引用验证**：解析AI生成的答案，提取引用的条款，与检索到的条款对比，确保引用准确。如果不准确，可重新检索或提示人工检查。
6. **返回结果**：返回答案，并在答案中高亮引用，可点击查看条款详情。

## 19. 场景：请设计一个批处理接口，接收一个文件（如包含100个商品描述的CSV），调用AI批量生成对应的营销文案。需要考虑API的速率限制、处理进度反馈、以及部分失败时的处理（是全部失败还是继续剩余任务）。

**核心思路**：

1. **异步处理**：接口接收文件后，立即返回任务ID。后端异步处理批量任务。
2. **任务分解**：解析CSV文件，将每一行作为一个子任务。使用线程池或消息队列并行处理，但需控制并发数以遵守AI服务的速率限制。
3. **速率控制**：使用令牌桶等算法控制调用频率，避免触发AI服务的限流。
4. **进度反馈**：任务状态（待处理、处理中、已完成、失败）存储在数据库中。提供进度查询接口，返回已完成数量和失败数量。
5. **错误处理**：单个子任务失败时，记录错误原因，继续处理其他任务。支持重试机制，可配置重试次数。
6. **结果收集**：所有子任务完成后，生成结果文件（CSV），包含原始数据和生成的文案，以及处理状态。提供下载链接。
7. **部分失败**：允许部分成功，结果文件中标明失败的行和原因。用户可修正后重新提交失败的行。
8. **资源清理**：结果文件可设置过期时间，定期清理。



## 20. 场景：如何实现“AI结果缓存”？对于相同或高度相似的用户问题，直接返回缓存的结果，避免重复调用AI产生成本和延迟。请设计缓存键的生成逻辑（如对Prompt进行标准化和哈希），以及缓存的过期策略。

**核心思路**：

1. **缓存键设计**：对用户输入的Prompt进行标准化处理，如去除多余空格、转换为小写、归一化同义词等。然后计算哈希值（如MD5）作为缓存键。也可考虑将模型参数（如温度）纳入键中，因为不同参数可能导致不同输出。
2. **相似度匹配**：如果需要支持高度相似的问题，可以使用向量相似度。将问题向量化，缓存键为向量，查询时计算余弦相似度，如果相似度超过阈值，则返回缓存结果。但实现复杂，通常精确匹配已足够。
3. **缓存存储**：使用Redis等分布式缓存存储键值对。值包括AI响应内容、生成时间、消耗Token等。
4. **过期策略**：
   - 基于时间：设置固定过期时间（如24小时）。
   - 基于访问：每次访问续期。
   - 基于事件：当知识库更新时，使相关缓存失效。
5. **缓存更新**：缓存命中时直接返回。未命中时调用AI，将结果写入缓存。
6. **缓存穿透**：对于不存在的键，可缓存空值（短时间），防止恶意攻击。
7. **缓存预热**：对常见问题，可预先调用AI并缓存结果。
8. **监控**：监控缓存命中率，调整缓存策略。
