## 1. 场景：AI模型列表和配置信息变化不频繁但读取极其频繁。请设计一个多级缓存方案，使用Caffeine作为本地缓存，Redis作为分布式缓存，并解决缓存穿透、雪崩和一致性问题。

核心思路：

1. 缓存层级设计：
   - 第一级：Caffeine本地缓存，每个应用实例独享，提供纳秒级读取速度，设置较短过期时间（如30秒）。
   - 第二级：Redis分布式缓存，所有实例共享，设置较长过期时间（如5分钟），作为本地缓存未命中的后备。
   - 第三级：数据库持久化存储，作为最终数据源。
2. 缓存加载策略：
   - 查询时先查本地缓存，命中则返回。
   - 未命中则查Redis，命中则更新本地缓存后返回。
   - 两者都未命中则查数据库，将结果写入Redis和本地缓存。
   - 本地缓存过期时间较短，避免实例间数据不一致时间过长。
3. 缓存穿透解决方案：
   - 布隆过滤器：在查询前检查键是否存在，但需维护布隆过滤器。
   - 缓存空值：当数据库查询为空时，在Redis中缓存空值（设置较短过期时间），避免频繁查询数据库。
   - 接口层校验：对明显非法的请求参数直接拒绝。
4. 缓存雪崩解决方案：
   - 差异化过期时间：在基础过期时间上增加随机偏移，避免大量缓存同时失效。
   - 热点数据永不过期，后台定时刷新。
   - 使用锁或队列控制数据库查询的并发，避免缓存失效时大量请求打到数据库。
5. 数据一致性问题：
   - 采用“先更新数据库，再删除缓存”的策略。
   - 数据库更新后，通过消息队列或Redis发布订阅通知所有实例删除本地缓存，再删除Redis缓存。
   - 设置合理的缓存过期时间，保证最终一致性。
6. 监控与维护：
   - 监控各层缓存命中率，调整缓存策略。
   - 使用Caffeine的统计功能监控本地缓存效果。



## 2. 场景：用户与AI的对话历史可能非常长（上万条）。请设计数据库表结构来存储这些历史，并支持高效地：1）按会话分页查询；2）模糊搜索对话内容；3）归档旧对话。你会使用什么类型的数据库和索引策略？

核心思路：

1. 数据库选型：
   - 主数据库：使用PostgreSQL或MySQL 8.0+，支持JSON类型和全文索引。
   - 搜索优化：对于模糊搜索，可结合Elasticsearch提供高性能搜索。
   - 归档存储：对于历史数据，可迁移到列式数据库（如ClickHouse）或对象存储。
2. 表结构设计：
   - 会话表（conversations）：存储会话元数据，包含会话ID、用户ID、标题、创建时间、最后活跃时间、状态、总消息数、总令牌数等。
   - 消息表（messages）：存储具体消息，包含消息ID、会话ID、消息序号、角色、内容、令牌数、时间戳。可考虑将大文本内容分离到单独的表或使用TOAST（PostgreSQL）存储。
3. 索引策略：
   - 按会话分页查询：在messages表创建复合索引(conversation_id, created_at DESC)，支持按会话和时间排序分页。
   - 模糊搜索对话内容：使用数据库全文索引（如PostgreSQL的gin_trgm_ops或MySQL的全文索引），或集成Elasticsearch建立倒排索引。
   - 归档查询：对conversations表的created_at字段创建索引，支持按时间范围快速定位待归档会话。
4. 分区与分表策略：
   - 按时间分区：将messages表按月或按周分区，提高查询性能，简化归档操作。
   - 按用户分片：对于海量用户，考虑按用户ID分库分表。
5. 归档策略：
   - 定义归档规则：如6个月前的会话标记为可归档。
   - 使用数据库事件或调度任务定期将历史数据迁移到归档表或冷存储。
   - 提供统一的查询接口，自动路由到当前表或归档表。



## 3. 场景：在RAG系统中，需要将知识库文档切片并向量化后存入向量数据库（如Milvus, Pinecone）。请描述Java后端如何与向量数据库交互，实现“给定问题，检索最相关的N个文本片段”的流程。

**核心思路**：

1. **文档预处理管道**：
   - 文档解析：使用Apache Tika、POI等库解析各种格式文档（PDF、Word、HTML等）。
   - 文本切片：按段落、句子或固定长度进行切片，保留上下文重叠。
   - 向量化：调用嵌入模型（如OpenAI Embedding、本地Sentence Transformers）将文本转换为向量。
   - 元数据提取：记录每个切片的来源文档、页码、位置等信息。
2. **向量数据库交互**：
   - 使用向量数据库的Java SDK（如Milvus Java SDK）或REST API客户端。
   - 建立连接池管理连接，配置连接参数和超时设置。
   - 设计数据模型：向量集合、向量ID、向量数据、元数据字段。
3. **检索流程**：
   - 问题向量化：将用户问题通过相同的嵌入模型转换为向量。
   - 相似度搜索：调用向量数据库的搜索接口，传入问题向量，指定返回数量N和相似度阈值。
   - 结果处理：获取返回的相似向量及其元数据，按相似度排序。
4. **结果优化**：
   - 重排序（Reranking）：使用更精细的交叉编码器对初步结果进行重新排序。
   - 结果去重：去除内容高度重复的片段。
   - 上下文组装：将选中的文本片段与问题组装成Prompt，提供给大模型。
5. **缓存策略**：
   - 缓存常见问题的检索结果，避免重复向量化和搜索。
   - 使用两级缓存：本地缓存（Caffeine）存储热点问题，分布式缓存（Redis）存储更多结果。
6. **监控与优化**：
   - 监控向量搜索的延迟和准确率。
   - 定期评估和优化嵌入模型、切片策略和搜索参数。



## 4. 场景：为了防止API密钥被盗用，我们不应该在前端硬编码，而应由后端代理。请设计一个安全的密钥管理方案：如何存储、轮换密钥，并在代理请求时将其安全地添加到请求头中？如何为不同内部服务分配不同权限的密钥？

**核心思路**：

1. **密钥安全存储**：
   - 使用专业的密钥管理服务（KMS），如AWS KMS、Azure Key Vault、HashiCorp Vault，或自建基于硬件的安全模块（HSM）。
   - 禁止在代码、配置文件、日志中硬编码密钥。
   - 开发、测试、生产环境使用不同的密钥。
2. **代理服务架构**：
   - 前端请求不带密钥，只带用户认证令牌。
   - 后端代理服务验证用户权限，从密钥管理服务获取对应密钥。
   - 代理服务构造请求，将密钥添加到请求头，转发给AI服务。
   - 代理服务记录审计日志，监控异常使用。
3. **密钥轮换策略**：
   - 定期自动轮换密钥，如每90天。
   - 使用密钥版本控制，新旧密钥并存一段时间，平滑迁移。
   - 轮换后更新密钥管理服务，无需重启应用。
4. **多服务密钥分配**：
   - 为每个内部服务创建独立API密钥，记录服务标识、权限范围、配额限制。
   - 权限控制：在代理服务中，根据当前请求的服务标识和应用场景，选择具有相应权限的密钥。
   - 配额管理：为每个密钥设置独立配额，超出配额时自动切换或拒绝。
5. **密钥使用监控**：
   - 实时监控每个密钥的使用情况：调用次数、令牌消耗、错误率。
   - 异常检测：识别密钥泄露迹象，如从不常见IP调用、频率异常。
   - 自动熔断：当检测到异常时，自动禁用密钥并告警。
6. **紧急响应机制**：
   - 支持密钥的即时吊销和替换。
   - 提供密钥使用历史查询，便于安全审计。



## 5. 场景：用户上传的文档可能包含公司机密。在发送给第三方AI服务前，必须进行脱敏。请设计一个可拓展的脱敏框架，支持通过正则、关键词列表和机器学习模型识别敏感信息（如身份证号、手机号），并将其替换为占位符。

**核心思路**：

1. **脱敏框架架构**：
   - 定义脱敏处理器接口，包含识别（identify）和替换（replace）方法。
   - 实现多种处理器：正则表达式处理器、关键词处理器、机器学习模型处理器。
   - 使用责任链模式，将多个处理器串联，每个处理器负责一类敏感信息。
2. **处理器设计**：
   - 正则处理器：预定义常见敏感模式（身份证、手机号、邮箱、银行卡号），支持自定义正则。
   - 关键词处理器：加载敏感词库，支持模糊匹配和词性分析。
   - 机器学习处理器：集成NER（命名实体识别）模型，识别自定义实体类型。
3. **处理流程**：
   - 文档解析：将各种格式文档转换为统一文本格式。
   - 敏感信息识别：各处理器并行或串行识别，生成敏感信息位置列表。
   - 位置合并：合并重叠的识别结果，避免重复替换。
   - 脱敏替换：根据敏感类型替换为相应占位符（如"[PHONE]"、"[ID_CARD]"）。
4. **可扩展性设计**：
   - 通过SPI机制支持自定义处理器。
   - 处理器配置化，支持动态加载和卸载。
   - 支持处理器优先级，确保高精度处理器优先执行。
5. **性能优化**：
   - 对处理器结果缓存，相同内容避免重复处理。
   - 支持流式处理，避免大文档内存溢出。
   - 机器学习模型批量处理，提高吞吐量。
6. **质量保证**：
   - 提供脱敏效果评估工具，计算召回率和准确率。
   - 支持人工审核和修正，形成反馈闭环优化模型。
   - 记录脱敏日志，支持审计和追溯。

6. **准确性保证**：
   - 端到端精确一次语义：生产者使用事务消息，消费者保证幂等处理。
   - 对账机制：定期对比消息队列消费位置与数据库记录，发现差异触发补偿。
   - 数据修正：支持历史数据重新计算，修复统计错误。
7. **查询优化**：

   - 使用列式存储（如ClickHouse）存储历史数据，支持快速分析查询。



## 7. 场景：某些恶意用户可能通过脚本高频调用“代码生成”接口，消耗大量资源。请实现一个基于滑动时间窗口的分布式限流（使用Redis），针对用户ID和接口两个维度进行限制。

**核心思路**：

1. **限流算法选择**：

   - 滑动时间窗口算法：精确控制任意时间窗口内的请求数，相比固定窗口更平滑。
   - 使用Redis有序集合（Sorted Set）实现，成员为请求ID，分数为时间戳。

2. **限流键设计**：

   - 用户维度：`rate_limit:user:{userId}`
   - 接口维度：`rate_limit:api:{apiPath}`
   - 用户+接口维度：`rate_limit:user:{userId}:api:{apiPath}`

3. **Redis Lua脚本实现**（保证原子性）：

   ```
   -- 参数：KEYS[1]=限流键，ARGV[1]=当前时间戳，ARGV[2]=窗口大小(毫秒)，ARGV[3]=最大请求数
   local key = KEYS[1]
   local now = tonumber(ARGV[1])
   local window = tonumber(ARGV[2])
   local max = tonumber(ARGV[3])
   
   -- 移窗口外的旧请求
   redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
   
   -- 获取当前请求数
   local current = redis.call('ZCARD', key)
   
   if current >= max then
       return 0 -- 超过限制
   end
   
   -- 添加当前请求
   redis.call('ZADD', key, now, now .. ':' .. math.random())
   redis.call('EXPIRE', key, window/1000 + 1) -- 设置过期时间
   return 1 -- 允许通过
   ```

4. Java集成：
   - 使用Spring Data Redis的 `RedisTemplate` 执行Lua脚本。
   - 在拦截器或AOP切面中调用限流脚本。
   - 如果返回0，抛出 `RateLimitExceededException`，返回HTTP 429状态码。

5. 多维度组合限流：
   - 先检查用户维度，再检查接口维度，都通过才允许请求。
   - 支持不同维度不同限制，如用户每分钟10次，接口每分钟1000次。

6. 动态配置：
   - 限流参数配置化，支持热更新。
   - 支持针对不同用户等级设置不同限制。

7. 监控与调试：
   - 记录限流触发日志，便于分析攻击模式。
   - 暴露限流指标，如拒绝请求数、当前活跃请求数。



## 8. 场景：AI生成的内容（如营销文案）需要入库前审核。请设计一个异步审核流水线：内容先入待审表，由审核服务（人或AI）处理，审核结果通过消息队列回写。如何保证内容状态同步的最终一致性？

**核心思路**：

1. **流水线设计**：
   - 内容生成后，状态为"待审核"，写入待审表，发送消息到"review-task"队列。
   - 审核服务消费任务，进行审核（人工审核或调用审核AI）。
   - 审核完成，发送结果到"review-result"队列。
   - 内容服务消费审核结果，更新待审表记录状态。
2. **状态管理**：
   - 待审表字段：内容ID、内容、状态、创建时间、审核结果、审核时间、审核人。
   - 状态流转：待审核 → 审核中 → 审核通过/驳回。
3. **最终一致性保证**：
   - 消息可靠性：生产者使用事务消息，确保消息不丢失；消费者手动确认，处理成功后才提交ack。
   - 幂等性：审核结果处理需幂等，防止重复消费导致状态错误。
   - 补偿机制：定时扫描待审表中长时间处于"审核中"状态的任务，重新投递到审核队列。
4. **异常处理**：
   - 审核服务失败：消息重试，超过最大重试次数进入死信队列，人工介入。
   - 结果处理失败：同上，进入死信队列，人工处理。
5. **数据一致性检查**：
   - 定期对账：对比待审表状态与消息队列消费位置，发现不一致触发告警。
   - 提供手动同步接口，支持强制更新状态。
6. **性能优化**：
   - 审核任务分片，支持并行审核。
   - 审核结果批量处理，减少数据库压力。
7. **监控**：
   - 监控各环节处理延迟，设置阈值告警。
   - 监控消息积压情况，及时扩容处理能力。



## 9. 场景：用户对话中包含了大量的Base64编码。导致单条记录巨大。请设计存储策略：是将图片单独存储到对象存储（如S3），数据库中只存URL，还是使用数据库的LOB字段？各自的考量是什么？

**核心思路**：

1. **方案对比分析**：
2. **方案A：对象存储 + 数据库存URL**
   - 优点：
     - 数据库体积小，查询性能高
     - 对象存储专为大文件设计，成本低
     - 支持CDN加速，图片访问快
     - 存储容量无限扩展
   - 缺点
     - 架构复杂，需要维护对象存储
     - 数据一致性管理复杂（需保证数据库记录和对象存储文件同步）
     - 删除时需要清理两处数据
     - 网络延迟可能影响访问速度
3. **方案B：数据库LOB字段**
   - 优点：
     - 强一致性，事务管理简单
     - 备份恢复一致，便于管理
     - 无需维护额外存储服务
   - 缺点：
     - 数据库体积膨胀，影响备份恢复速度
     - 查询性能可能下降（特别是大字段）
     - 数据库存储成本通常更高
     - 有最大字段长度限制
4. **混合方案**：
   - 小图片（<100KB）存数据库，大图片存对象存储。
   - 实时对话中的图片存数据库保证低延迟，历史对话图片定期迁移到对象存储。
5. **推荐方案**：
   - 对于AI对话场景，推荐使用对象存储方案，因为：

6. **安全配置**：对于API密钥等敏感配置，应使用配置中心的加密存储功能，确保安全。
7. **多环境支持**：通过配置中心的命名空间（Namespace）和分组（Group）功能，支持多环境配置管理。
8. **客户端容错**：当配置中心不可用时，客户端应使用本地缓存的上一次配置，保证服务可用性。
9. **监控与审计**：记录配置变更历史，便于审计。监控配置推送状态，确保各个实例配置一致。



## 19. 场景：设计一个“资源包”模型，用户购买一定额度的Token包。每次AI调用后，实时扣除相应Token。请设计数据库表结构和扣减逻辑，确保在高并发下不会超卖，并能给出精确的余额提示。

**核心思路**：

1. **数据库表设计**：
   - 资源包表（package）：记录资源包的定义，如包ID、名称、Token数量、价格等。
   - 用户资源包表（user_package）：记录用户购买的资源包，包括用户ID、包ID、购买时间、剩余Token、状态（有效、过期、用完）等。
   - 消费记录表（consumption_log）：记录每次Token消耗，包括用户ID、资源包ID、消费Token数、时间、关联的AI请求ID等。
2. **扣减逻辑**：
   - 每次AI调用时，根据用户ID和使用的模型，计算消耗的Token数。
   - 从用户资源包中选择一个可用的资源包（按购买时间先后或剩余Token数），扣除相应Token。
   - 扣除操作需要保证原子性，可以使用数据库的乐观锁或悲观锁。
3. **高并发扣减**：
   - 使用数据库行锁（如SELECT ... FOR UPDATE）锁定用户资源包记录，然后检查剩余Token是否足够，足够则扣减，最后提交事务。这种方式在并发高时可能成为瓶颈。
   - 使用乐观锁：在用户资源包表中增加版本号字段，扣减时先读取剩余Token和版本号，扣减后更新，并在更新条件中带上版本号。如果更新失败（版本号变化），则重试。
   - 使用Redis原子操作：将用户剩余Token存储在Redis中，使用 `DECRBY` 命令进行扣减，该命令是原子的。然后异步将扣减结果同步到数据库。但需要注意Redis和数据库的数据一致性。
4. **余额提示**：在扣减前，可以先查询剩余Token，如果不足，可以提前返回错误。但由于并发扣减，查询的余额可能不准确，因此需要在扣减时再次检查。
5. **多资源包支持**：用户可能有多个资源包，需要设计策略选择哪个包优先使用（如先过期先使用，或按购买顺序）。
6. **事务一致性**：Token扣减和AI调用应该在一个分布式事务中，或者使用最终一致性。可以采用本地消息表，先扣减Token，记录消息，然后进行AI调用，如果AI调用失败，则回滚Token。
7. **监控与告警**：监控资源包使用情况，当剩余Token低于阈值时，提醒用户续费。



## 20. 场景：AI生成的内容可能需要符合不同地区的法律法规（如GDPR的“被遗忘权”）。请设计一个功能，允许用户导出其所有数据，并永久删除。这涉及到哪些服务的数据清理？如何保证删除的彻底性？

**核心思路**：

1. **数据范围识别**：首先，需要识别用户数据分布在哪些服务和存储中。常见的包括：用户基本信息、对话历史、生成的内容、操作日志、支付记录、反馈等。
2. **导出功能**：
   - 提供导出接口，用户可以通过该接口请求导出所有数据。
   - 后端收集所有相关服务的数据，按照规定的格式（如JSON）打包，并提供下载链接。考虑到数据量可能很大，可以采用异步方式，先创建导出任务，完成后再通知用户下载。
3. **删除功能**：
   - 用户请求删除数据时，需要确保所有相关服务的数据都被删除。
   - 设计一个统一的数据清理服务，该服务调用各个微服务的删除接口，删除该用户的数据。
   - 删除操作应该是物理删除，而不仅仅是逻辑删除。对于数据库，使用DELETE语句；对于文件存储，删除文件。
4. **服务调用**：数据清理服务通过RPC或消息队列通知各个服务执行删除。每个服务负责删除自己存储的数据，并返回删除结果。
5. **彻底性保证**：
   - 所有服务必须提供删除接口，并且删除操作要彻底，包括备份数据、日志等。
   - 对于数据库，要删除相关表的所有记录，并考虑外键约束。
   - 对于文件存储，要删除用户上传的文件和生成的内容。
   - 对于搜索引擎或缓存中的索引，也要删除。
6. **审计跟踪**：记录用户数据导出和删除的请求，包括时间、IP、操作人等，以便审计。
7. **延迟删除**：有些数据可能因为法律要求需要保留一段时间，可以根据数据保留策略，标记为待删除，稍后再实际删除。
8. **测试与验证**：定期进行数据清理的测试，确保删除功能有效。可以通过创建测试用户，执行导出和删除，然后检查各个存储是否还有残留数据。
9. **合规性**：确保数据导出和删除流程符合GDPR等法规的要求，例如在规定时间内完成（如30天）。
