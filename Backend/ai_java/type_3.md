# 类别三：状态管理、业务流程与架构



## 1. 场景：请为“AI智能客服工单处理”设计一个状态机。状态包括`待分配`、`AI处理中`、`等待人工`、`已解决`等。触发事件包括`用户回复`、`AI推荐方案`、`人工接管`。请画出状态转移图，并用Java枚举和状态模式实现核心逻辑。

核心思路：

1. 状态与事件枚举：首先，定义状态枚举（`TicketState`）和事件枚举（`TicketEvent`）。

   - 状态包括`PENDING`（待分配）、`AI_PROCESSING`（AI处理中）、`WAITING_MANUAL`（等待人工）、`RESOLVED`（已解决）等。

   - 事件包括`USER_REPLY`（用户回复）、`AI_SUGGESTION`(AI推荐解决方案)、`MANUAL_TAKEOVER`（人工接管）等。

2. 状态转移规则：明确状态转移的条件。例如

   - 从`PENDING`，在`USER_REPLY`事件后，可以转移到`AI_PROCESSING`（由AI自动处理）。
   - 从`AI_PROCESSING`，在`AI_SUGGESTION`事件后，可以转移到`WAITING_MANUAL`（AI无法解决，转人工）或者`RESOLVED`（AI提供方案并解决）。
   - 从`AI_PROCESSING`，在`MANUAL_TAKEOVER`事件后，直接转移到`WAITING_MANUAL`。
   - 从`WAITING_MANUAL`，在`USER_REPLY`事件后，可以保持在`WAITING_MANUAL`（继续人工处理）或转移到`RESOLVED`（人工解决）。
   - 从任何状态，都可以在特定事件下转移到`RESOLVED`。

3. 状态机实现：使用状态模式，将每个状态的行为封装在对应的状态类中。也可以使用枚举状态机（如使用`switch`语句）或使用Spring State Machine框架。如果业务逻辑复杂，建议使用Spring State Machine，它提供了状态机和DSL，可以清晰定义状态、事件、转移和动作。

4. 状态持久化：工单的状态需要持久化到数据库。在状态改变时，更新工单记录的状态字段，并可能记录状态转移的历史日志。

5. 动作执行：在状态转移的过程中，可以触发相应的业务动作，例如，当进入`AI_PROCESSING`时，自动调用AI处理服务；当进入`WAITING_MANUAL`时，通知客服人员。

6. 异常处理：考虑非法状态转移的处理，例如，从`RESOLVED`状态不能再转移到其他状态（除非重新打开）。可以在状态机中定义非法转移的异常处理。



## 2. 场景：在分布式部署中，如何实现一个分布式的、可重入的锁，来保证“为同一用户生成月度报告”的定时任务在同一时刻只有一个实例执行？请对比基于Redis和基于ZooKeeper的实现方案。

核心思路：

1. 需求分析：需要为每个用户（用用户ID区分）生成月度报告，同一个用户的报告生成任务不能并发执行，但不同用户之间可以并行。锁需要具有可重入性，即同一个线程（或实例）可以多次获取锁，避免死锁。锁需要设置超时时间，防止任务失败导致锁无法释放。
2. 基于Redis的实现：
   - 使用Redisson客户端，它提供了可重入锁`RLock`，并支持自动续期。锁的Key可以设计为`"report:lock:{userId}"`。
   - 原理：通过Redis的Lua脚本保证原子性，利用Hash结构记录锁的持有者和重入次数，设置锁的租期（leaseTime），并通过看门狗机制（watchdog）在任务执行期间自动续期。
   - 优点：性能高，实现简单。
   - 缺点：基于超时，存在锁提前释放的风险（如果网络延迟导致续期失败），也可能因为时钟漂移出现问题。
3. 基于ZooKeeper的实现：
   - 使用Curator框架，它提供了可重入锁`InterProcessMutex`。锁的路径可以设计为`/locks/report/{userId}`。
   - 原理：利用ZooKeeper的临时顺序节点和Watcher机制。锁的持有者对应一个临时节点，其他竞争者监听前一个节点。可重入性通过同一个线程在同一节点下创建多个临时节点来实现。
   - 优点：可靠性高，不存在超时问题，锁释放及时。
   - 缺点：性能比Redis低，需要维护ZooKeeper集群，增加了系统复杂度。
4. 选择建议：如果对性能要求高，且可以容忍极端情况下锁失效（报告重复生成，但可能可以接受），可以选择Redis。如果对可靠性要求极高，不允许重复执行，且系统已经有ZooKeeper集群，则可以选择ZooKeeper。
5. 注意事项：无论哪种方案，都需要在任务开始时获取锁，任务完成后释放锁。释放锁时，必须判断锁的持有者，避免释放了其他实例的锁。



## 3. 场景：用户与AI的对话会话（`ChatSession`）需要支持分布式集群中的任意节点访问。你会如何设计这个会话对象的存储、检索和过期策略？请比较将会话状态存储在Redis与存储在数据库中的利弊。

核心思路：

1. 会话数据结构：`ChatSession`通常包含会话ID、用户ID、创建时间、最后活跃时间、消息列表、一些上下文信息（如Token使用统计）等。消息列表可能较大，且增长快。
2. 存储方案比较：
   - Redis：
     - 优点：读写性能极高，支持丰富的数据结构（如Hash、List），可以方便地存储和更新会话的各个字段。支持设置过期时间，可以自动清理过期会话。支持发布订阅，可以用于会话事件的通知。
     - 缺点：数据存储在内存，容量有限，成本较高。持久化可能有一定延迟，存在数据丢失风险（取决于持久化策略）。不适合存储极大的消息历史（除非进行分片或压缩）。
   - 数据库（如MySQL、MongoDB）：
     - 优点：数据持久化可靠，存储容量大，成本相对较低。支持复杂的查询和事务操作。可以存储完整的消息历史，便于后续分析。
     - 缺点：读写性能远低于Redis，尤其是频繁更新和读取的场景。无法直接支持过期自动删除，需要额外任务清理。
3. 设计建议：采用混合存储策略，利用各自的优势。
   - 热数据：当前活跃的会话（如最近24小时内）存储在Redis中，以保证低延迟访问。会话结构可以用Hash存储，消息列表用List存储，并设置合理的过期时间（如48小时）。
   - 冷数据：当会话一段时间不活跃（如超过24小时），将其从Redis迁移到数据库中长期存储。可以通过一个定时任务，将过期会话同步到数据库，然后从Redis删除。
   - 检索：首先从Redis中查找会话，如果找不到，再从数据库加载（并可能回写到Redis，如果再次活跃）。
4. 过期策略：在Redis中设置会话Key到过期时间，例如24小时不活动则过期。在数据库中，可以设置一个最后更新时间字段，并建立定时任务清理非常旧的会话（如30天前）。
5. 分布式访问：无论存储在Redis还是数据库，都可以被集群中的任意节点访问。关键是要保证会话ID的唯一性，并且会话的存储是中心化的（即所有节点访问同一个存储服务）。



## 4. 场景：当AI调用外部工具（如查询库存、创建日历事件）失败时，系统应进入“等待修复”状态，并通知人工。请用状态模式或Spring State Machine实现此流程，并考虑失败重试和超时机制。

核心思路：

1. 状态定义：定义任务的状态，例如`PROCESSING`（处理中）、`WAITING_FOR_TOOL`（等待外部工具调用）、`WAITING_FOR_HUMAN`（等待人工干预）、`COMPLETED`（完成）、`FAILED`（失败）等。
2. 状态转移：
   - 任务开始后，状态为`PROCESSING`。
   - 当需要调用外部工具时，状态转移到`WAITING_FOR_TOOL`，并发起异步调用。
   - 如果外部工具调用成功，状态转移回`PROCESSING`，继续后续步骤。
   - 如果外部工具调用失败，根据重试策略，可以重试（状态可能保持在`WAITING_FOR_TOOL`或进入重试子状态）。当重试次数用尽，状态转移到`WAITING_FOR_HUMAN`，并发通知（如邮件、短信）给相关人员。
   - 人工干预后，可以手动触发重试或修复，状态转移回`WAITING_FOR_TOOL`或`PROCESSING`。
3. 失败重试机制：为重试设置次数上限（如3次）和退避策略（如指数退避）。每次重试失败，更新重试计数。重试计数达到上限后，触发人工干预。
4. 超时机制：为每个状态（特别是`WAITING_FOR_TOOL`）设置超时时间。如果超过预定时间没有状态转移，则触发超时处理，可以自动重试或直接进入`WAITING_FOR_HUMAN`。
5. 实现方式：使用Spring State Machine，可以很方便地定义状态、事件、转移和动作。在状态机的动作（Action）中，可以调用业务服务，例如调用外部工具。在状态机的错误处理中，可以捕获异常，并根据条件决定重试或转移状态。
6. 持久化：状态机的状态需要持久化，以便在应用重启后能恢复。Spring State Machine支持多种持久化方式，如Redis、MongoDB、关系型数据库。
7. 通知人工：当状态进入`WAITING_FOR_HUMAN`时，触发一个通知动作，调用通知服务发送警报。



## 5. 场景：请用DDD（领域驱动设计）的思想，对“AI绘画订单”进行领域建模。识别核心聚合根（`Order`）、实体（`ImageTask`）、值对象（`PaintingStyle`）和领域事件（`OrderCreated`，`ImageGenerated`）。

**核心思路**：

1. **领域分析**：AI绘画订单的核心是用户下单，选择绘画风格、尺寸等参数，系统生成图片，用户可能下载或分享。订单会有支付、生成状态、结果图片等概念。
2. **聚合根**：`Order` 是聚合根，每个订单有唯一的订单ID，负责维护订单的一致性边界。订单内部包含一个或多个 `ImageTask`（实体），因为一个订单可能包含多张图片（例如，同一个提示词生成多张供选择）。订单还包含用户ID、创建时间、总价、订单状态等属性。
3. **实体**：`ImageTask` 是实体，有唯一的任务ID，属于某个订单。它包含生成图片的具体参数（如提示词、风格、尺寸）、生成状态、生成的图片URL等。实体有生命周期，状态会变化。
4. **值对象**：`PaintingStyle` 是值对象，描述绘画风格，例如风格名称、描述、对应的模型参数等。值对象没有唯一标识，不可变，可以共享。其他值对象可能包括 `ImageSize`（宽高）、`Price`（金额，包含货币和数值）等。
5. **领域事件**：
   - `OrderCreated`：订单创建时发布，事件内容包含订单ID、用户ID、创建时间等。可能触发支付流程、风控检查等。
   - `ImageGenerated`：图片生成完成时发布，事件内容包含订单ID、任务ID、图片URL、生成状态等。可能触发通知用户、更新订单状态等。
6. **领域服务**：有些业务逻辑不适合放在聚合根或实体中，例如，生成图片的AI调用可能是一个领域服务 `ImageGenerationService`，它接受 `ImageTask` 的参数，调用外部AI服务，并返回结果。
7. **仓储**：`OrderRepository` 负责聚合根的持久化，提供保存、根据ID查询等方法。`ImageTask` 的持久化由 `Order` 聚合根管理，不单独提供仓储。
8. **工厂**：订单的创建可能比较复杂，可以使用工厂模式（`OrderFactory`）来封装创建逻辑，确保创建出的订单是有效的。
9. **模块划分**：可以将订单相关的领域模型、领域服务、仓储等放在一个模块中，例如 `order` 模块。



## 6. 场景：用户编辑了已提交给AI处理的Prompt，需要取消旧任务并启动新任务。请设计一个`TaskManager`服务，管理任务的生命周期，并确保状态变更的原子性（如从`PROCESSING`到`CANCELLED`）。

**核心思路**：

1. **任务模型**：定义 `Task` 实体，包含任务ID、关联的业务ID（如对话ID）、状态（`PENDING`，`PROCESSING`，`COMPLETED`，`CANCELLED`，`FAILED`）、创建时间、开始时间、结束时间、结果等。任务状态变更必须是原子的，即同一时间只能有一个状态。
2. 任务管理服务：`TaskManager`提供以下核心方法：
   - `submitTask()`：提交新任务，初始状态为 `PENDING`，并触发任务执行（或由任务调度器异步执行）。
   - `cancelTask(taskId)`：取消指定任务。如果任务状态是 `PENDING`，直接改为 `CANCELLED`。如果任务状态是 `PROCESSING`，需要先调用外部AI服务的取消接口（如果支持），然后将状态改为 `CANCELLED`。如果任务已经是终态（`COMPLETED`，`FAILED`，`CANCELLED`），则取消操作无效。
   - `updateTaskStatus(taskId, newStatus)`：内部方法，用于原子更新任务状态。通常使用乐观锁（如版本号）或悲观锁（数据库行锁）来保证原子性。
3. **原子性保证**：在数据库中更新任务状态时，使用条件更新。例如：
4. `UPDATE task SET status = 'CANCELLED', version = version + 1 WHERE task_id = ? AND status = 'PROCESSING' AND version = ?;`
5. 如果更新影响的行数为0，说明状态已经改变，取消操作失败（或已经结束）。在Java代码中，可以使用JPA的 `@Version` 注解实现乐观锁。
6. **取消外部任务**：对于正在处理的任务，取消时需要调用AI服务的取消接口。这是一个异步过程，可能成功也可能失败。即使AI服务取消失败，本地任务状态也应该改为 `CANCELLED`，并记录取消失败的原因。可以考虑在任务结果中记录"任务被用户取消，但AI服务未能及时停止"。
7. **启动新任务**：在取消旧任务的同时，可以立即创建一个新任务，并关联到同一个业务ID。注意处理旧任务取消和新任务创建之间的竞争条件，确保业务上只有一个活跃任务（如果需要）。
8. **事件驱动**：任务状态变更时，可以发布领域事件，如 `TaskCancelled`，其他组件（如前端）可以监听这些事件，更新UI或进行后续处理。



## 7. 场景：在事件驱动架构下，`UserMessageReceivedEvent`事件会触发AI处理。但同一用户可能在极短时间内发送多条消息。如何确保对于同一会话，AI处理是串行的，避免回答错乱？请基于消息队列（如Kafka分区键）设计解决方案。

**核心思路**：

1. **问题分析**：如果不加控制，同一会话的多个消息事件可能被并发处理，导致AI回复的顺序错乱，或者后发的消息先被处理，造成上下文混乱。
2. **消息队列分区策略**：利用Kafka的分区有序特性。确保同一个会话的所有消息都被发送到同一个分区，这样同一个分区内的消息就是有序的，消费者按顺序处理。
3. **设计细节**：
   - 生产者：在发布 `UserMessageReceivedEvent` 时，以会话ID（`sessionId`）作为Kafka消息的Key。Kafka会根据Key的哈希值将消息分配到特定的分区。这样，相同会话ID的消息一定会被分配到同一个分区。
   - 消费者：启动多个消费者实例，每个分区只能被同一个消费者组中的一个消费者消费。这样，同一个会话的消息只会被同一个消费者处理，从而保证了串行处理。
4. **处理性能**：如果某个会话的消息量非常大，可能会导致单个分区成为热点。但通常情况下，单个用户的消息频率是有限的，所以热点问题不大。如果确实有超级热点会话，可以考虑进一步拆分（例如，按子会话ID分区），但需要权衡有序性的需求。
5. **状态管理**：消费者在处理消息时，可能需要维护会话的上下文（如对话历史）。由于同一个会话的消息是串行处理的，所以可以在消费者内存中维护一个会话上下文缓存（如使用 `ConcurrentHashMap`），在处理完一个消息后更新上下文。但要注意消费者实例失败的情况，可能需要将上下文持久化到外部存储（如Redis）中。
6. **错误处理**：如果某条消息处理失败，可以重试，但重试可能会阻塞后续消息的处理。需要根据业务决定是跳过失败的消息（移到死信队列）还是不断重试。通常，对于AI处理，可以允许跳过少数失败的消息，以免阻塞整个会话。
7. **扩展**：如果AI处理耗时较长，可以考虑在消费者内部使用一个线程池来处理，但需要保证同一个会话的消息在同一个线程中处理，仍然保持串行。这可以通过一个会话ID到处理线程的映射来实现，但复杂度较高。更简单的方式是增加分区数量，让更多的消费者并行处理不同会话的消息。



## 8. 场景：请设计一个“工作流引擎”的数据模型，用于支持用户拖拽配置包含AI节点、判断节点、人工审核节点的流程。如何持久化这个流程图，并在运行时解释执行？

**核心思路**：

1. **数据模型设计**：
   - `WorkflowDefinition`：工作流定义，包含ID、名称、版本、创建时间等。
   - `Node`：节点基类，包含节点ID、类型（AI节点、判断节点、人工审核节点等）、位置信息等。可以用JSON字段存储节点配置（如AI节点的模型、参数，判断节点的条件表达式，人工审核节点的审核人）。
   - `Connection`：连接线，表示节点间的流向。包含源节点ID、目标节点ID、条件（对于判断节点出来的连接，可能有一个条件表达式，如"通过"或"拒绝"）。
   - 可以使用一张表存储所有节点，用 `type` 字段区分节点类型，用 `config` 字段（JSON）存储节点特定配置。连接线单独一张表。
2. **持久化**：将整个工作流定义保存到数据库。可以使用关系型数据库，用上述表结构存储。也可以使用文档数据库（如MongoDB），将一个完整的工作流定义作为一个文档保存，这样读取更快，但查询和更新部分内容可能不便。
3. **运行时解释执行**：
   - 工作流实例：当触发一个工作流时，根据定义创建一个 `WorkflowInstance`，包含当前状态（如运行中、完成）、当前节点指针、上下文变量等。
   - 节点执行器：为每种节点类型实现一个执行器（`NodeExecutor`）。例如：
     - `AiNodeExecutor`：调用AI服务，获取结果，将结果存入上下文。
     - `DecisionNodeExecutor`：根据条件表达式和上下文变量，决定走哪条连接线。
     - `ManualReviewNodeExecutor`：创建一个审核任务，等待人工处理，处理结果返回后继续。
   - 流程引擎核心：一个状态机，从开始节点开始，根据节点执行器的结果和连接线，决定下一个节点，直到结束节点。流程引擎需要支持异步等待（如人工审核），因此需要持久化工作流实例的状态。
4. **上下文变量**：工作流实例需要一个上下文，用于存储流程中的变量（如输入数据、AI输出、审核结果等）。上下文通常是一个 `Map<String, Object>`，可以序列化后存入数据库。

## 11. 场景：我们需要为每个AI对话会话维护一个“上下文令牌窗口”。当新消息加入时，如果超出窗口大小，需要按特定策略（如FIFO、或基于重要性的裁剪）移除旧消息。请设计一个线程安全的TokenWindow类来实现此逻辑。

**核心思路**：

1. **数据结构选择**：使用一个双端队列（如 `ArrayDeque`）来按顺序存储消息，同时维护一个当前总令牌数的计数器。每个消息对象应包含其内容的令牌数。另外，可能需要一个优先队列（如基于重要性的评分）来支持按重要性裁剪，但通常FIFO策略下双端队列即可。
2. **线程安全实现**：使用 `ReentrantLock` 或 `synchronized` 关键字来保护所有修改操作（添加消息、移除消息）。由于每个会话的TokenWindow是独立的，我们可以将会话级别的锁细化，避免全局锁争用。
3. **添加消息逻辑**：
   - 当新消息加入时，计算其令牌数，并加上当前总令牌数。
   - 如果未超过窗口大小，则直接将消息加入队列尾部，更新总令牌数。
   - 如果超过窗口大小，则根据策略移除旧消息：
     - **FIFO策略**：从队列头部开始移除消息，直到总令牌数不超过窗口大小。
     - **基于重要性的裁剪**：这需要为每条消息维护一个重要性分数，通常需要在添加消息时计算或由外部传入。我们可以使用一个优先队列来按重要性排序，但移除时可能需要从中间移除，因此数据结构可能更复杂。一种简化方法是每次添加时，如果超出窗口，则移除当前队列中重要性最低的消息，直到满足窗口大小。这可能需要维护两个数据结构：一个队列保证顺序，一个按重要性排序的结构（如平衡树）来快速找到重要性最低的消息。
4. **移除消息的清理**：从队列中移除消息时，需要从总令牌数中减去对应消息的令牌数，并可能触发一些清理操作（如标记消息已被移出上下文）。
5. **考虑复杂度**：FIFO策略实现简单，时间复杂度低。基于重要性的裁剪可能需要O(log n)的时间复杂度来维护和移除。需要根据实际需求权衡。
6. **扩展性**：可以定义裁剪策略接口，支持不同策略的切换。TokenWindow类可以接收一个策略实例，在构造时注入。

5. **分布式环境考虑**：单机限流只能限制单个实例的流量，如果有多台实例，则需要分布式限流。可以使用Redis等分布式缓存，通过Lua脚本保证原子性，实现分布式令牌桶。

## 16. 场景：在“AI辅助编程”场景，需要维护文件的编辑历史（类似迷你Git）。请设计一个版本管理的数据结构，支持提交更改、查看差异、以及回滚到某个AI建议之前的版本。

**核心思路**：

1. **数据结构**：使用版本树（类似Git的提交树）。每个版本（提交）包含以下信息：版本ID（哈希）、父版本ID（可能多个，但这里简化可以只支持线性历史）、更改内容（差异diff）、提交时间、提交者、提交信息等。
2. **存储**：可以使用数据库表存储版本信息，表结构包括：版本ID、文件ID、父版本ID、diff内容（或完整内容）、提交信息等。如果存储完整内容，则回滚时直接获取；如果存储diff，则需要从初始版本开始应用所有diff直到目标版本，才能得到该版本的内容。
3. **提交更改**：当用户或AI对文件进行更改并提交时，生成一个diff（可以使用差异算法，如Myers差分算法），并创建一个新版本记录，其父版本为当前版本。然后更新当前分支指向新版本。

5. **回滚**：回滚到某个AI建议之前的版本，实质上是将当前文件内容替换为目标版本的内容。可以创建一个新版本，其内容为目标版本的内容，父版本为当前版本，这样不会丢失历史。或者，可以像Git一样，通过重置当前分支指针到目标版本（强制回滚），但这样会丢失回滚点之后的版本，需要谨慎。
6. **性能考虑**：如果文件很大，存储完整内容会占用大量空间，而存储diff则节省空间但读取时需要计算。可以权衡：定期存储完整内容作为快照，中间版本存储diff。

2. **客户端监听**：每个应用实例启动时，从配置中心获取开关的当前值，并监听该配置的变化。当配置发生变化时，配置中心会推送新值到所有监听的应用实例。
3. **降级逻辑**：在请求处理入口（如拦截器、过滤器、ControllerAdvice）中，检查开关状态。如果开关打开，则将所有请求（或特定路径的请求）重定向到静态提示页面，或者直接返回静态提示信息，不再调用AI服务。
4. **生效机制**：配置中心通常采用长轮询或推模式，将配置变更实时通知到所有订阅的客户端。因此，当管理员在配置中心将开关打开时，所有应用实例会在短时间内（几秒内）收到新配置，并立即生效。
5. **灰度发布**：如果需要，可以结合配置中心的灰度发布功能，先对部分实例开启降级，验证无误后再全量开启。
6. **开关权限**：该开关应由运维或负责人控制，只有特定权限的人可以修改。
7. **监控与告警**：降级开关开启时，应触发告警通知相关人员，以便及时处理AI服务故障。同时，监控系统应记录降级期间的请求量和用户体验。



## 18. 场景：在微服务架构下，“用户服务”发生“用户注销”事件。“AI对话服务”需要监听此事件，并清理该用户的所有会话缓存和临时文件。请描述如何通过消息总线可靠地实现这一跨服务数据同步。

**核心思路**：

1. **事件发布**：当用户注销时，用户服务发布一个"用户注销"事件到消息总线（如Kafka）。事件内容至少包含用户ID、注销时间戳。
2. **事件可靠性**：用户服务在本地事务中记录用户注销状态，并发送事件到Kafka。可以使用事务消息确保事件发送和业务操作的一致性，即要么都成功，要么都失败。
3. **事件订阅**：AI对话服务订阅"用户注销"事件的主题。当收到事件时，根据用户ID清理该用户的会话缓存（如Redis中的会话数据）和临时文件（如对象存储中的文件）。
4. **幂等处理**：由于消息可能重复，AI对话服务需要幂等处理。可以在处理事件时，先检查用户是否已注销（可以在本地数据库记录已处理的注销事件），避免重复清理。
5. **错误处理**：如果清理过程中发生错误（如缓存删除失败），可以将消息重新放入队列重试，或者记录错误日志，人工介入。
6. **最终一致性**：由于消息传递的延迟，用户注销后可能短暂时间内还能看到历史会话，但最终会被清理，这符合最终一致性。
7. **监控**：监控事件处理延迟和失败率，确保数据同步的及时性。



## 19. 场景：请为”AI模型训练任务”设计一个状态模型，包含QUEUED, DATA_PREPROCESSING, TRAINING, EVALUATING, DEPLOYING, COMPLETED, FAILED等状态。并考虑如何在任务失败时，根据失败原因（如数据错误、资源不足）提供重试建议。

**核心思路**：

1. **状态定义**：明确每个状态的含义和转换关系。例如：
   - QUEUED: 任务已提交，等待资源。
   - DATA_PREPROCESSING: 数据预处理中。
   - TRAINING: 模型训练中。
   - EVALUATING: 模型评估中。
   - DEPLOYING: 模型部署中。
   - COMPLETED: 任务成功完成。
   - FAILED: 任务失败。
2. **状态转换**：设计状态转换图，规定哪些状态之间可以转换。例如，从QUEUED可以转换到DATA_PREPROCESSING，从DATA_PREPROCESSING可以转换到TRAINING，等等。失败（FAILED）可以从任何中间状态转换。
3. **失败原因分类**：失败原因可以归类，例如：
   - 数据错误：数据不存在、数据格式错误、数据量不足等。
   - 资源不足：内存不足、GPU不足、存储空间不足等。
   - 环境错误：依赖库版本问题、环境变量缺失等。
   - 超时：任务执行超过最大允许时间。
4. **重试建议**：根据失败原因，系统可以提供重试建议。例如：
   - 数据错误：检查数据路径和格式，修复后重试。
   - 资源不足：等待资源释放或申请更多资源后重试。
   - 环境错误：检查环境配置，修复后重试。
   - 超时：增加超时时间后重试，或优化算法。
5. 可以在任务失败时，记录失败原因和错误详情，然后根据原因代码给出建议。这些建议可以预置在配置中，也可以由管理员自定义。
6. **状态机实现**：可以使用Spring State Machine或简单的枚举状态机来实现。状态转换时触发相应的动作，如状态变更日志、通知等。
7. **持久化**：任务状态需要持久化到数据库，以便重启后恢复。



## 20. 场景：在订单履行流程中，AI用于生成产品描述。但描述生成后需要人工审核。请设计一个“审批工作流”，支持多级审批、驳回修改、以及审批通过后自动上架。如何用状态机和任务队列实现？

**核心思路**：

1. **状态设计**：订单项（或产品）的状态包括：待生成描述、描述生成中、待审核、审核中、审核通过、审核驳回、已上架等。
2. **工作流步骤**：
   - 步骤1：订单创建后，触发AI生成产品描述，状态转为"描述生成中"。
   - 步骤2：生成完成，状态转为"待审核"，创建审核任务，进入审核队列。
   - 步骤3：审核员领取任务，状态转为"审核中"。
   - 步骤4：审核员操作：通过或驳回。
     - 如果通过，状态转为"审核通过"，触发自动上架流程。
     - 如果驳回，状态转为"审核驳回"，并通知相关人员修改。修改后重新提交审核，状态回到"待审核"。
   - 步骤5：自动上架流程，状态转为"已上架"。
3. **多级审批**：可以在审核任务中设置多级审批，每级审批人都可以是通过或驳回。驳回时可以回到上一级或直接打回修改。可以通过审批链配置来定义各级审批人。
4. **状态机实现**：使用状态机（如Spring State Machine）来管理状态流转。状态转换的条件包括：事件（如生成完成、审核通过、审核驳回）和守卫条件（如当前审核级数）。
5. **任务队列**：使用任务队列（如Redis队列或消息队列）来管理审核任务。当状态变为"待审核"时，向队列中添加一个审核任务。审核员从队列中获取任务。任务队列可以支持优先级、超时等特性。
6. **驳回修改**：当审核驳回时，状态机转换到"审核驳回"，并通知原提交人。原提交人修改后，重新触发审核流程，状态回到"待审核"，并重新进入审核队列。
7. **自动上架**：审核通过后，状态机转换到"审核通过"，然后触发一个自动上架的动作，调用上架服务，上架成功后状态转为"已上架"。
8. **扩展性**：审批工作流的配置（如审批人、审批级数）可以从数据库或配置中心动态加载，以便灵活调整。
