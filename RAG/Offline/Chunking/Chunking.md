## 1. 核心概念

Chunking（分块）是将原始文档切分为适合检索与生成的片段，是 RAG 数据处理链路的重要环节。

分块策略会同时影响两个环节：

- **Retrieval**：片段是否能被准确召回、相关内容能否排在前面。
- **Generation**：召回的片段是否包含足够完整的上下文，能否支持模型生成答案。

因此，分块不是越细越好，也不是越大越好。设计目标是在**检索粒度、语义完整性、上下文充分性和存储成本**之间取得平衡。

Chunking 决定了检索系统能够获取什么内容。如果切分时破坏了关键语义、上下文或结构，Embedding 和 Reranker 也无法凭空恢复已经丢失的信息。因此，Chunking 是 RAG 检索链路的重要基础。



## 2. 主流分块策略

| 策略 | 基本原理 | 优点 | 局限 | 适用场景 |
| --- | --- | --- | --- | --- |
| 固定大小分块（Fixed-size） | 按字符数或 Token 数切分 | 简单、速度快、易于控制片段长度 | 可能切断句子、段落或完整论述 | 简单文本、日志、快速建立基线 |
| 滑动窗口分块（Sliding Window） | 固定大小切分，并让相邻块保留部分重叠 | 降低边界处信息丢失的风险 | 增加存储与 embedding 成本，可能产生重复召回 | 连续性较强的文本 |
| 递归分块（Recursive） | 按分隔符优先级，从较大的结构边界逐步细分 | 尽量保留自然边界，适用范围广 | 依赖分隔符配置；不保证每个块在语义上都完整 | 通用文档，常用默认方案 |
| 句子／段落分块 | 按句子或段落等自然边界切分 | 结构直观，易于保留局部语义 | 片段长度可能差异较大 | 结构清晰的文章、FAQ |
| 语义分块（Semantic） | 根据相邻句子的语义变化识别切分点 | 有机会使片段主题更集中 | 需要额外 embedding 或模型计算；效果依赖阈值与最小／最大块长 | 主题边界不规则的长文本 |
| 文档结构感知分块（Structure-aware） | 利用标题、章节、段落、表格等原始结构切分 | 保留文档层级与来源信息 | 依赖文档解析质量，不同格式需要不同处理 | Markdown、技术文档、PDF、手册 |
| 父子分块（Parent-Child） | 小块用于召回，命中后取对应父块提供上下文 | 兼顾精确定位与上下文完整性 | 需要维护父子映射，生成上下文可能变长 | 长文档、层级清晰的知识库 |



### 2.1 Fixed-size Chunking

按预设的字符数或 Token 数直接切分，例如每块约 512 tokens。

- **优点**：实现简单，片段长度可控，适合作为 baseline。
- **缺点**：切分点不考虑语义和文档结构，可能把一句话、表格或论证拆开。



### 2.2 Recursive Chunking

递归分块按分隔符优先级尝试切分：优先使用较大的自然边界；如果片段仍超过长度限制，再尝试更细的边界。

例如：

```text
段落边界（空行）
  → 行边界（换行）
  → 句子边界（如 。！？）
  → 词边界（如空格）
  → 字符边界
```

不同语言和 splitter 的默认分隔符可能不同。中文文档应根据实际文本补充 `。`、`！`、`？`、`；` 等分隔符。

LangChain 示例：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)

chunks = splitter.split_text(text)
```



### 2.3 Semantic Chunking

一种常见做法是：

1. 将文档拆成句子或较小的文本单元。
2. 对各单元计算 embedding。
3. 计算相邻单元之间的语义相似度或语义距离。
4. 在语义变化较明显的位置切分，并结合块长限制进行调整。

语义分块的目标是让每个 chunk 的主题更集中，但它并不必然优于递归分块。块过小可能提高局部匹配的精确度，却让生成模型缺少回答问题所需的上下文；额外的 embedding 计算也会增加处理成本。



### 2.4 Document Structure-aware Chunking

根据原始文档结构切分，而不是只依赖固定长度或文本相似度。例如：

- 按标题层级保留章节路径。
- 尽量不拆散列表、代码块和表格。
- 将文档标题、章节标题等信息作为 metadata 保存。
- 当单个结构单元过长时，再在内部使用递归切分。



### 2.5 Parent-Child Chunking

将文档组织为不同粒度的块：

- **Child chunk**：较小的片段，用于检索和精确定位。
- **Parent chunk**：较大的片段，例如所属段落或章节；命中 child 后，可取回 parent 作为生成上下文。

这种方式尝试同时满足检索的精确性和生成所需的上下文完整性。父块不一定必须是整篇文档，具体粒度应根据文档结构与上下文窗口确定。





## 3. Chunk Size 与 Overlap

### 3.1 Chunk Size：块大小

Chunk size 决定每个片段包含多少内容。不存在适用于所有语料的固定最优值，可先用一个合理范围建立基线，再通过检索和生成评测调整。

| 块大小 | 可能的优点 | 可能的问题 |
| --- | --- | --- |
| 较小 | 主题集中，检索定位更精细 | 论述、定义或条件可能被拆开，生成时上下文不足 |
| 较大 | 更容易保留完整论述与必要背景 | 无关内容增加，相关信息可能被稀释，影响召回；上下文占用更高 |

**常见起始配置：**可尝试 256–512 tokens，并根据任务调整。它是实验起点，不是通用最优值。若使用按字符计量的 splitter，不能直接把字符数参数当作 Token 数。



### 3.2 Overlap：相邻块重叠

Overlap 是相邻 chunk 之间重复保留的内容，用于降低关键信息恰好落在切分边界、导致上下文断裂的风险。

- 常见起始范围可设为块大小的约 10%–20%。
- Overlap 太小，边界处的信息仍可能不完整。
- Overlap 太大，会增加存储和 embedding 成本，也可能让检索结果包含大量重复内容。

例如，若 chunk size 为 500 tokens，可以从约 50–100 tokens 的 overlap 开始测试。



### 3.3 如何判断块太大或太小？

- **块太大**：无关内容混入较多，匹配粒度变粗，相关内容可能被稀释；同时占用更多上下文窗口。
- **块太小**：定义、条件、步骤或论证可能被拆开，召回片段缺少回答所需的前后文。
- **Overlap 过大**：相邻块高度重复，增加成本，并可能导致 Top-K 结果被近似重复片段占据。

不能只看检索命中率判断分块效果。还应观察召回片段是否包含完整证据，以及最终答案的正确性与完整性。





## 4. 不同文档类型的分块方式

| 文档类型 | 建议处理方式 | 注意事项 |
| --- | --- | --- |
| Markdown／技术文档 | 按标题层级和段落组织，超长章节再递归切分 | 保留标题路径、章节等 metadata |
| PDF | 先进行版面与文本解析，再根据段落、标题、页码等结构切分 | 表格、双栏排版、页眉页脚和扫描图片需要单独处理 |
| 表格 | 尽量保留表头与对应行；必要时按行组或业务记录切分 | 不要让数据行脱离列名与单位 |
| 代码 | 优先按模块、类、函数或完整代码块切分 | 保留文件路径、符号名和相关注释 |
| FAQ | 将问题与对应答案放在同一块 | 超长答案可分层切分，同时保留问题与标题信息 |
| 日志 | 按事件、记录或时间窗口切分 | 保留时间戳、服务名、级别、请求 ID 等元数据 |
| 法律／制度文档 | 优先保留条款、章节及其编号 | 不要把适用条件、例外条款与主体规定拆散 |





## 5. Metadata 与层级信息

Metadata 用于描述 chunk 的来源和属性，常见字段包括：

- `document_id`：原始文档标识。
- `title`：文档标题。
- `section`：章节或标题路径。
- `page`：页码。
- `source`：来源地址或文件路径。
- `created_at` / `updated_at`：文档时间信息。
- `access_control`：权限相关信息（如适用）。

Metadata 可用于检索过滤、结果溯源、权限控制和上下文组织。它与 chunk 正文不同：metadata 描述文档或片段的属性，不应把所有结构信息都无差别地拼进正文。





## 6. Chunking 设计与优化

调整 Chunking 通常需要重新切分并重新生成 Embedding，属于一次性离线成本。相比直接升级 Embedding 模型或引入更复杂的检索组件，先优化分块是值得尝试的低复杂度方案。

1. **看数据**：先确认语料是 Markdown、PDF、FAQ、代码、日志还是表格，尽量利用其天然结构。
2. **建立基线**：通用文本可从简单方案开始，确定初始 chunk size 与 overlap。
5. **构建评测**：通过 Eval 检查召回质量、上下文完整性和最终答案质量做对照实验，判断 Chunking 是否构成瓶颈。
5. **引入 Reranker**：如果候选文档的排序存在问题，再加入重排序优化。
6. **按需升级**：根据评测结果，再考虑更换 Embedding 模型、Late Chunking 或 Contextual Retrieval 等。
